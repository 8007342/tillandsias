# Design — stable-upgrade-converge

Status: **proposed**. OPEN items wait for the operator (end of file).

## 1. When it runs

The converge pass runs **once per installed stable version**, triggered by an
event, never a timer:

- after `tillandsias --update` (1490-gttj) installs a stable release;
- after the 1490-gttj background check silently installs one (that check's
  24-hour cadence is already proposed and approved there; this change adds no
  cadence);
- after a manual curl install of a stable release.

A marker `state/converged-<version>` records success. A host already marked
does nothing. A crash part-way leaves no marker, so the next tray start resumes
the pass. Every step below is idempotent.

Prereleases do not trigger it. A smoke host can run it by hand with
`tillandsias --converge`.

## 2. The rule for every reused component

For each component, in the order of §3:

1. **Upgrade in place**, fully. Packages to latest, image rebuilt for the new
   version tag, binary replaced.
2. **Verify** with a check specific to the component (below). If it passes,
   the component is converged.
3. If the upgrade fails, the verify fails, or the component is marked
   *must-regenerate*: **throw it away and rebuild it from scratch**. Only that
   component; never its neighbours, never the never-thrown-away set (§5).
4. If the rebuild also fails: mark it `converge-failed:<component>`, show it in
   the tray and `--diagnose`, and leave the rest of the host running. No
   automatic HARD reset.

*Must-regenerate* means the component has no upgrade-in-place path: a
container image is always rebuilt for a new version, never patched.

## 3. Order of operations

```
0  binary handoff                  1490-gttj (host, then guest hot-install)
1  guest OS upgrade                macOS VM / Windows distro: dnf upgrade --refresh
2  enclave images                  vault, proxy, git, router, nix-cache, inference, catalog
3  shared stack swap               only when no running forge depends on it (1490-gttj skew policy)
4  forge base images               rebuilt for the new version tag
5  prune                           old images and stale owned objects, by label
6  reboot-pending                  a new guest kernel takes effect at the next idle VM restart
```

Why this order:
- The binary first, because every later step is run by the new binary.
- The guest OS before images, because images are built inside the guest and
  must build against the upgraded host userland.
- The shared stack after its images exist, so a swap is never left waiting on a
  build.
- Forges last, because they are per-launch and the least shared.

## 4. Per platform and per component

| Component | Linux | macOS | Windows | Verify |
|---|---|---|---|---|
| guest OS | n/a (host OS is the operator's) | `dnf -y upgrade --refresh` in the VM (the same block as #801's provisioning) | the same in the `tillandsias` distro | dnf exits 0; `rpm -Va --nofiles` reports no broken deps |
| guest kernel | n/a | installed by the upgrade; active after the next VM restart (step 6) | WSL kernel is Microsoft's; distro packages only | `uname -r` equals the newest `kernel-core` after the restart |
| enclave images | rebuilt for `v<NEW>` | the same, in the guest | the same, in the distro | the image builds; its label `io.tillandsias.image.version` = NEW |
| shared stack containers | recreated from the new image when no forge depends (skew policy) | the same | the same | the container is healthy, and its readiness event (1922-rann) arrives |
| forge base images | rebuilt for `v<NEW>` | the same | the same | the image builds; a no-op forge start passes |
| Linux toolboxes | OPEN (Q4) | n/a | n/a | — |

**Regenerate from scratch:**
- An image or container is removed and rebuilt.
- A **guest OS whose upgrade fails** is regenerated by rebuilding the guest
  disk:
  - **macOS:** `rootfs.img` from the pinned base image plus the #801 upgrade.
    The identity disk, and the Vault store on it, are kept (the existing SOFT
    contract).
  - **Windows:** the Vault store lives *inside* the distro
    (`/root/.tillandsias/vault`), so regenerating the distro is a HARD reset
    and would lose it. Windows therefore does NOT regenerate the distro
    automatically; it marks `converge-failed:guest-os` and asks (OPEN Q2).

## 5. Never thrown away

These survive every converge step, whatever fails:

- **The Vault store:** governed by `host-state-lifecycle`'s dispositions
  (`Verified:KEEP`, `Unverified:KEEP`, `Absent:REINIT-AT-INIT`). A converge
  pass is SOFT: it never clears the keyring share or the root token, and never
  deletes the store.
- **The model cache:** `cache_root()/models`, host-side on macOS and Linux.
  Windows keeps it in the distro (1182-2vaz), which is one more reason the
  Windows distro is never regenerated automatically.
- **Projects:** cloud repos, the git mirrors (`tillandsias-mirror-*`) and any
  pushed work. A forge's unpushed work is the agent's responsibility (forges
  are `--rm`, commit-to-persist).
- **`downloads/`, `config/`, keyring items** (`vault-shamir-share-v1`,
  `vault-root-token-v1`, the install anchor).

## 6. Running forges

- A running forge is **never stopped** by a converge pass. It keeps its old
  image until it exits on its own. The new image serves only new launches.
- Step 3 (the shared-stack swap) waits until no running forge depends on the
  old container. That is the 1490-gttj skew policy, which waits for an event and
  does not poll. Until then the host runs old and new side by side, within the
  declared compatibility window.
- Lenovinha's tray-restart-keeps-forges work (filed separately) is what makes a
  tray restart during converge safe. This change depends on it, and the
  guest-kernel reboot (step 6) waits for zero running forges.
- An agent can opt in early with `forge.reload` (fleet-durable-instructions),
  which writes its resume note and restarts it on the new image.

## 7. Rollback: fix forward

- No downgrade. `downgrade_refusal` already refuses one, and this change does
  not add a rollback path.
- A component that cannot converge stays on its freshly rebuilt state, or is
  marked `converge-failed`. The tray shows one plain sentence naming it. The
  next stable release is the fix.
- A converge pass that wedges the host (it must not; every step is bounded) is
  recovered by the existing SOFT reset, which the converge pass is built from.

## OPEN questions for the operator, in plain words

1. **Guest kernel reboot.** A new kernel only takes effect after the VM
   restarts. May Tillandsias restart the VM automatically the next time no
   forge is running, or should it wait for you to quit and reopen the tray?
2. **Windows guest that fails to upgrade.** On Windows the Vault lives inside
   the Linux distro, so rebuilding the distro would lose your sign-ins. Should
   Tillandsias (a) ask you first, (b) keep the old distro and just report the
   failure, or (c) move the Vault out of the distro (a bigger change, like
   macOS's separate identity disk)?
3. **Prereleases.** Should the converge pass run on daily prereleases too, or
   only on stable (as you said)? Smoke hosts can always run it by hand.
4. **Linux toolboxes.** `tillandsias-builder` and `tillandsias-nix` are your
   toolboxes, not ours by label. Should a stable install upgrade them too, or
   leave them alone?
5. **How loud.** When a component is rebuilt from scratch successfully, should
   the tray tell you, or only when something fails?
