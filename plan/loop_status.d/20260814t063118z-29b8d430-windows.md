## Cycle - windows (windows-next)

- 690-eug2 partial again (2 of 5 sub-defects now done; stays ready). Fixed the
  O(n^2) needle rescan: the expect driver re-searched the entire unmatched
  transcript on every frame, worst exactly when the transcript is longest and
  the exchange is already in trouble.
- The correctness risk was the whole job. A needle can straddle a frame
  boundary, so the cursor backs up by needle.len()-1. A PTY delivers output in
  whatever chunks the kernel chooses, so a prompt split across frames is normal.
  Off by one and matches are lost SILENTLY.
- Every existing test in the file feeds each needle in ONE frame, so none would
  have caught it. Added a test delivering the prompt ONE BYTE PER FRAME.
- HAND-FALSIFIED, and the failure mode is the point: setting the overlap to 0
  did not fail cleanly - the test HUNG 60+ seconds then failed, because the
  driver waited for a prompt it had already been sent. That is the
  silent-loss-as-timeout shape, reproduced. Restoring returned 26/26.
- Did NOT do the transcript cap, deliberately: ExecOutput.stdout is a public
  field callers parse, so capping changes an observable contract, and dropping
  from the front invalidates the very search indices this cycle made
  load-bearing. That needs a recorded decision about what a caller receives on
  truncation, not a late-night guess.
