- **The defect, as the code showed it**: four outcomes shared one representation. `cloud_projects.rs` returned a bare `Vec` documented as *"always well-formed — empty on missing binary, missing auth, non-zero exit, malformed JSON"*, and an account with genuinely zero repos produced the identical value. `CloudRefreshReply` had no ok/err field, so the tray inferred "confirmed empty" from a message that only ever meant "here is a list". **Well-formed is not the same as informative, and that doc line was the defect written down as a feature.**
- **Added `CloudRefreshOutcome { Ok, Failed { reason }, Unknown }`** with a `#[serde(default)]` field, and an `is_confirmed()` predicate so `Unknown` cannot be forgotten at a call site the way `matches!(.., Failed{..})` invites.
- **`Unknown` IS THE DEFAULT ON PURPOSE — the mixed-version half.** A guest predating the field serializes no `outcome`, serde fills `Unknown`, the host treats the list as unconfirmed. Defaulting to `Ok` would make an old guest's *failures* read as confirmed answers, which is the bug this type exists to end. **Fail closed: an absent discriminator is not a success discriminator.** Same reasoning as CAP_EXEC_ARGV_VECTOR's feature-detect in 795-zshi.
