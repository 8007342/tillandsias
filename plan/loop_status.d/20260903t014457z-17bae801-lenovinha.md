envelope — it reported PASS on every run it ever made and would have reported

I VERIFIED THE SWEEP RATHER THAN TRUSTING IT. The dispatch said five, one file,
lines 31/36/41/46/51. The guard I wrote finds exactly those and nothing else
across 411 files. Same answer, independently derived — and the guard had to

THE JUDGEMENT CALL, which the coordinator routed here deliberately. Fixing the
tautologies alone leaves the test inspecting a container it launched ITSELF
with the flags typed on its own command line: every repaired step would ask
podman to confirm flags the test just supplied. A real question about podman
and none about Tillandsias. A step can be perfectly falsifiable and still
measure the wrong system. So the launch argv is now derived from
MANDATORY_HARDENING_FLAGS in policy.rs, and a new step asserts that
declaration is complete — delete a flag there and the test launches without it
and the enforcement steps fail.

WHERE I STOPPED, and the header now says so where a reader will look: this
still does not prove production call sites APPLY the envelope.
validate_launch_argv has zero production call sites, which is 972-6vaj.
Turning this fixture into a call-site audit was the over-fix; leaving it
silently implying that coverage was the under-fix.

THREE BUGS IN MY OWN REPAIR, ALL THE SAME FAMILY AS THE DEFECT, and all caught
because I dry-ran the shell instead of reading it.
  1. `xargs podman run ... < flags -- IMAGE sleep 300` APPENDS, so the flags
     landed after the image and after `sleep 300`. The container would have
     launched with no hardening at all.
  2. `grep -qxF "$want"` parses a `--`-prefixed pattern as an option, so the
     envelope step could NEVER pass — the mirror image of the original defect,
     a step that always fails rather than always passes. Needs -e.
  3. The guard's own fixture caught a hole in the guard: 'X' and "X" compared
     unequal, so a quote-style change evaded it.
That the fixture for a guard-against-tests-that-cannot-fail immediately caught
the guard failing to catch something is the best argument for it I have.
