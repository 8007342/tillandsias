### 895-bkrn — measured the untested half, and it killed my own proposal

This packet's deliverable offered "the checkout **or at minimum CARGO_TARGET_DIR**",
and I had argued in its context that the partial move "may capture most of the win
at a fraction of the risk, since the build writes far more than it reads."

**Prediction registered before measuring**, including its falsifying branch: the
slowest step is the plan archiver, which does not live in `target/`, so I expected
a partial win — and said that if the gate barely moved, the deliverable must change.

**Measured, quiescent tree (`1c9d5b417` before and after), forced warm gate, 350s:**

| | | |
| --- | ---: | ---: |
| cargo (test + 2× clippy) | 37.0s | **10.6%** |
| plan ledger I/O (archiver 105.1, arrival 21.6, MO-FULL 18.1) | 144.8s | 41.4% |
| tree-wide hashing (ghost-trace ratchet 41.2, gate stamp 28.3) | 69.5s | 19.9% |
| other scripts | 57.8s | 16.5% |

**`CARGO_TARGET_DIR` could touch at most 37s of 350s — and only if a native target
dir made cargo free, which it would not.** The cheap option does not exist.

The bridge cost is not in BUILDING. It is in **reading the ledger and hashing the
tree** — 41% plan/ I/O, 20% walking ~4600 files for a digest. Both are pure 9P file
I/O inside the checkout, and neither cares where cargo writes.

Direction of my prediction: right. Magnitude: worse than I guessed — I expected the
cargo portion to be substantial and it is a tenth.

**Deliverable narrowed to whole-checkout-only**, with the CARGO_TARGET_DIR half
REMOVED rather than left in place, because a future reader would otherwise take a
measured-not-to-work option as the low-risk path.

**Released back to `ready`, blocked on a DECISION rather than on work.** Relocating
the checkout re-plumbs every Git-Bash-side path that resolves
`./target/release/tillandsias-plan.exe` — every cycle of mine, the pre-push hook,
