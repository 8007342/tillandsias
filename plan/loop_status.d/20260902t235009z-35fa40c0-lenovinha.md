THE PACKET'S OWN PROPOSED RULE WAS FALSE AND THIS HOST FALSIFIED IT. I filed
964-r98h yesterday saying mem_info_vram_total "is absent or zero for an
integrated part". Measured here it is backwards in BOTH directions at once: the
discrete RTX 3070 exports no such file (it belongs to amdgpu, and the
proprietary NVIDIA driver does not provide it) and the integrated Vega exports
2 GiB (its BIOS UMA carve-out, which amdgpu reports as VRAM). A classifier built
on my own rule would have labelled each device as the other and passed review,
because the rule is plausible and matches what the field name suggests. Only a
machine carrying both kinds at once shows it up.

WHAT REPLACED IT: three sysfs rungs, each sound alone. Partially-CPU-visible
VRAM means memory behind an aperture, which only exists when the device owns it
(discrete; the pre-resizable-BAR signature). A prefetchable BAR at or above 1
GiB is an aperture only dedicated memory has (discrete; the ReBAR case, and how
the 3070 is classified at 8192 MiB). Fully-visible VRAM with no large aperture
is a UMA carve-out (unified; the Vega, 2 GiB behind a 256 MiB BAR). Anything
else is None. Rung 3 is the weak one and its limit is written in the code
rather than hidden.

NO VENDOR TABLE, deliberately, and it costs something. 0x10de would have
classified the NVIDIA card for free and correctly, and it would have been a
guess — the packet exists because `unified` is wrong for a discrete Radeon and
`discrete` is wrong for every iGPU in the fleet. A non-resizable-BAR NVIDIA card
on another host will read `undetermined`. That is the right answer, not a
regression.
