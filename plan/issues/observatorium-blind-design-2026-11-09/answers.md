Top-level keys: schemaVersion, epoch, definitions, measuredAt, revision, release, dirty, shallow, current, gaps. current = {specs{files,requirements,scenarios}, plan{total,states,source,fragments}, residual{value,denominator,satisfied,measured,source,reason,histogram{declared,traced,positively_tested},traced,positivelyTested,reasons,records,provenance{revision,measuredAt,dirty,gradeSchema,gradeSha256,artifact,recordScope,limitations,obligationsSha256,staticSha256,scopeSha256,population,excluded,invariantsExcluded,populationGaps{unregistered,missing,unkeyed}}}}. ## 1. Machine-readable obligation registry? Assumption: partly
- Yes for ID, spec, requirement id, title, requirement text: target/observatorium-centicolon/obligations.json (rows with id, req_id, spec, title, requirement, spec_digest, must_tokens, traces), produced by scripts/lua/centicolon-extract.lua (schema centicolon-extract/1). Not committed; regenerated per run. Also carries population, excluded{deprecated,obsolete}, invariant_count, unregistered, missing, unkeyed.
- Per-obligation observed rows (id, req_id, spec, state, reason, optional host, regime) are produced by centicolon-grade-observed.lua in grade.json under `obligations`; observatorium/metrics/collect.mjs holds them in a `details.obligations` structure (id, req_id, spec, state, reason, host?, regime?, title?, requirement?), but snapshots.jsonl stores only the aggregate, not the rows.
- Not present: "kind", "evidence bar", "weight" fields. Obligations are scenario obligations plus requirements with no scenario (definitions.denominator in collect.mjs DEFINITIONS); invariants are excluded (provenance.invariantsExcluded: 126). Tombstones exist only as a registry `tombstone:` for obsoleted specs or an openspec/changes record (scripts/test-centicolon-ratchet.sh header), not as a per-obligation field in the export.
- Weights are declared in methodology/proximity.yaml (requirement signal weights such as litmus_positive_passes 0.20, runtime_trace_observed 0.15) but are not applied by the grader.

## 2. Per-obligation state recorded? Assumption: partly
- Recorded per obligation, but only three states are ever produced: declared, traced, positively_tested (scripts/lua/centicolon-grade-observed.lua: hist = {declared, traced, positively_tested}). Plus a `reason` per non-satisfied row: no-binding, unrun, failed, skipped, spec-changed (green for satisfied).
- The seven-value ordered lattice (absent, declared, traced, positively_tested, negatively_tested, runtime_observed, evidence_bundled) exists only declaratively in methodology/math-foundations.yaml (obligation_state.ordered_values). negatively_tested, runtime_observed, evidence_bundled are never assigned by code.
- No per-obligation "bar" field; the only bar is positively_tested counted as satisfied (satisfied = hist.positively_tested; R = denominator - satisfied).
- Not the CentiColon "score" as aggregate: the live aggregate is R (residual obligations count) / denominator / satisfied, not a weighted CentiColon earned score. Latest snapshot: denominator 1571, declared 1566, traced 5, positively_tested 0.

## 3. What is a "release"? Assumption: partly
- Snapshot key is `release` = git tag string "v<years-since-1970>.<month>.<day>.<build>" e.g. "v56.10.14.1", "v56.11.7.1" (observatorium/history/snapshots.jsonl; VERSION file is 56.11.7.1). 56 = 2026-1970; it IS a date-derived tuple (year offset, month, day, build).
- methodology/versioning.yaml describes an older format "v<Major>.<Minor>.<YYMMDD>.<Build>+<CommitHash>" (contract/phase semantics); the live VERSION/tags do not follow it (see Q12).
- Stable promotion is a separate channel event: scripts/promote-stable.sh moves the `stable` git tag and flips the GitHub release prerelease=false; snapshots are not flagged stable in snapshots.jsonl (no stable field). Snapshots are appended at release cut (`npm run release-snapshot`, observatorium/package.json -> scripts/build.mjs --release-snapshot).

## 4. Does grader emit denominator/earned/residual/regime; durable baseline? Assumption: partly (the plan to keep own history is right)
- Emitted per run: denominator, satisfied (earned), R (residual), histogram, residue_reasons, records, measured (bool), unmeasured_reason (grade.json; centicolon-grade-observed.lua). There is no total_cc/CentiColon-weighted earned figure in this grader.
- "Comparable/Broken" regime is not a grader output. Ratchet regime values are baseline | monotone | scope-added (and combined with +) per scripts/lua/check-centicolon-ratchet.lua; "Comparable" appears only in crates/tillandsias-plan/src/fragments.rs as perf-measurement comparability (Comparable / RefusedUnlocated / RefusedDifferentLoci / RefusedDifferentWorkloads), unrelated to the grade.
- Baseline: ratchet snapshot is <out>/last.txt (lines "<id> <state> <spec> <req_id>"), host-local, untracked under target/. No durable accepted-release baseline exists elsewhere.
- The committed observatorium/history/snapshots.jsonl IS a durable, committed per-release history of {denominator, satisfied, value(R), histogram, reasons, records, provenance}. Note: v56.10.14.1 row has residual.measured absent and lacks histogram; later rows have it. Release values: 1536/1567/1567/1567/1567/1571/1571 denominators, satisfied 0 throughout.

## 5. Platforms per obligation / per-platform status? Assumption: yes (attribution absent)
- No per-obligation required-platform field in obligations.json or grade.json. Grading selects by litmus digest and spec digest, not platform.
- A per-obligation `host` (and `regime`) is copied from the matching results record onto an observed row when satisfied (centicolon-grade-observed.lua: by_host = rec.host). Results records shape: {step, digest, status, host, regime, spec, spec_digest, ts}. host is a machine name, not an OS/platform label.
- The linux/windows/macos platform branches (linux-next, windows-next, osx-next) are workflow facts (CLAUDE.md), not a grader dimension.
