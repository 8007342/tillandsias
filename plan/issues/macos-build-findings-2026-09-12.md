**Findings**:

1. **The skill's own freshness gate (§1) produces a false STALE, and this run
   would have failed it.** §0 captures `HEAD_SHA`, but §1 recomputes
   `HEAD_SHA="$(git rev-parse --short HEAD)"` at assert time. Any commit made
   between build start and the assert — in this run, three ledger commits — moves
   HEAD and the gate then reports `STALE BINARY: --version git df944af67 !=
   HEAD 4eea1cbf0` for a binary that is in fact fresh. The binary is stale or not
   relative to the tree it was BUILT from; comparing against live HEAD measures
   how much ledger work happened since. Fix: assert against the §0-captured
   `HEAD_SHA`, or capture the SHA immediately before invoking the build.

2. **The skill's §2a `DIAG_EXIT` is always 0 and cannot detect the hard failure
   it exists to detect.** The snippet is
   `DIAG_JSON=$(... || true)` followed by `DIAG_EXIT=$?`. `$?` there is the exit
   status of the ASSIGNMENT, and `|| true` has already forced it to 0, so
   `DIAG_EXIT` is 0 even when `--diagnose --json` exits 1. The
   `section_kind=diagnose-hard-failure` arm is therefore unreachable as written.
   This run's exit 0 was captured WITHOUT the `|| true` mask and is genuine.
   Same shape as the two bugs `land-on-platform-branch.sh` documents in its own
   header: a pipeline/assignment status read as the status of the thing inside it.

3. **`guest_binary_staged_matches_bundle: false`** — staged
   `d677e5f5843d16de00dc5771fb23da3dcae8d7de3378420adc86c72f075dc3bb` (the
   2026-09-05 binary) vs bundle
   `6722be3b185b39b26260f1ac4204dee2b790e5baf33f191204e9116b9416ddf1` (today's).
   Reported correctly and loudly by `--diagnose`, which is the mechanism
