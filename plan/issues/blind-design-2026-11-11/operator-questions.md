# Operator questions raised by the blind designs (2026-11-11)

One decision per line. Each names the options and what each one costs.

- **OQ-1.** Name the floor host the product must work on, per platform — (a) 2 cores / 4 GB Linux and 8 GB macOS/Windows: every budget is sized for it and only one forge runs at a time; (b) 4 cores / 8 GB everywhere: two forges fit but 4 GB machines are refused at install; (c) the weakest current fleet host per platform as measured: budgets follow real hardware and move when the fleet changes.
- **OQ-2.** Say what "near-zero overhead" binds — (a) the tray process only: the VM and services may stay up while the tray runs, giving fast starts but a standing memory cost on macOS/Windows; (b) the whole product when no forge is open: the VM and services must stop by themselves, giving slower warm starts; and give the number you will hold us to (for example tray memory in MB and wakeups per minute).
- **OQ-3.** Decide what happens on a Linux desktop with no tray host (stock GNOME without the AppIndicator extension) — (a) command line plus one notification: nothing extra to ship, but no icon; (b) ship or require a tray host: an icon everywhere, but one more component to install and maintain.
- **OQ-4.** Say whether these designs must cover more than one machine now — (a) one machine, but nothing may block growing later: simplest, matches the capability ladder; (b) several machines in this round: adds host enrolment, cross-host identity and authenticated transport to every design.
- **OQ-5.** Decide whether Linux hosts without a systemd user session are supported — (a) no: refuse with one plain sentence; (b) yes: any design relying on systemd needs a second supervisor.
- **OQ-6.** Decide whether any record survives forge removal for audit — (a) nothing survives: auditing is live-only and incidents cannot be reconstructed later; (b) a typed record with no free text and no personal data is kept on the host for a fixed time (proposed 30 days): incidents can be reconstructed, at the cost of one persistent file.
- **OQ-7.** If an audit record is kept, decide what happens when it cannot be written — (a) credential grants stop: the trail is complete but a full disk stops all work; (b) grants continue and the gap is recorded afterwards: work continues but the trail has a hole.
- **OQ-8.** If an audit record is kept, decide whether it may name the upstream account — (a) no, only opaque ids: nothing personal at rest, weaker for investigations; (b) yes: more useful, but the file then holds personal data and needs encryption and a retention rule.
- **OQ-9.** Decide whether the host name an agent tried to reach counts as sensitive — (a) yes: only the owning forge sees it and the audit keeps a category; (b) no: the audit keeps exact hosts, which makes egress investigations much stronger and reveals what each project talks to.
- **OQ-10.** Decide whether project-chosen names (model, branch, image) may appear in events every forge sees — (a) no: other forges learn nothing, messages are vaguer ("a model is loading"); (b) yes: clearer messages, but one forge's choices become visible to the others.
- **OQ-11.** Decide whether swap must be encrypted — (a) required: forge memory that spills to disk is unreadable later, at the cost of setup work per platform and a refusal where it cannot be done; (b) not required: simpler, but log and secret pages can remain on disk after a forge closes.
- **OQ-12.** Approve or refuse a disk-space check every 5 minutes while a forge runs (12 wakeups per hour) — (a) approve: a filling disk is noticed before it breaks a forge; (b) refuse: disk is checked only when a forge starts or a download begins, and a full disk is found on failure.
- **OQ-13.** Decide whether a container started by a forge may see its parent's events or start containers of its own — (a) no: simplest and tightest; (b) yes, by explicit grant from the parent: sub-agents can follow the parent's work, with a larger surface to audit.
- **OQ-14.** Decide whether terminal scrollback on the host counts as forge logs that must die with the forge — (a) no: the user's terminal is the user's; (b) yes: forge terminals must open in a viewer of ours that keeps nothing.
- **OQ-15.** Give the scale to design for (forges at once, containers per forge) — (a) single digits of forges: current buffer sizes hold; (b) dozens: buffers and memory budgets grow, the floor host is refused at that scale.
- **OQ-16.** Decide whether a provider subscription sign-in may be used through a gateway that attaches the token outside the forge — (a) yes, after you review each provider's terms: no provider credential ever enters a forge; (b) no: subscription users keep a credential file inside the forge, as today, and each such forge is labelled as holding a live credential.
- **OQ-17.** Decide whether a malicious program running as the same user on the host is something the product must defend against — (a) no, basic hardening only: current shape holds; (b) yes: the credential holder must move to a separate OS user or hardware-held keys, a much larger build.
- **OQ-18.** Decide whether the product assumes full-disk encryption — (a) assumed and checked at start with a plain warning: hibernation and swap leaks are covered; (b) not assumed: the design must keep secrets out of swap and hibernation by itself and accept what remains.
- **OQ-19.** Decide what happens to the key that signs licence acknowledgements when the vault is wiped — (a) a new key is made and old records stay valid against the public key already committed: no user action, two keys in history; (b) old records must be re-acknowledged: one clean identity, at the cost of asking the user again.
