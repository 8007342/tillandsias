### 20260904T070534Z — ok (cold re-provision, 980-xcaf criterion 4 + 804-deux)

- build_run_id: 20260904T070534Z
- head_sha: 8bcd3d84f, version 56.9.2.1
- purpose: exercise the PROVISIONING path — which the section-3 smoke
  skipped, because that host was already provisioned — under the exact
  PATH a LaunchServices-started .app receives.

**WHY A PLAIN GUI LAUNCH COULD NOT BE USED — both `open` forms mask the bug**:
`open -a <name>` was already known to mask it. `open <path-to-.app>` masks
it TOO, and worse. Measured:
```
$ open "$HOME/Applications/Tillandsias.app"; sleep 8
$ ps eww -p 18569 | tr ' ' '\n' | grep '^PATH='
PATH=/Users/tlatoani/.local/bin:/usr/local/bin:…:/opt/homebrew/bin
```
That is the calling shell's PATH verbatim, `/opt/homebrew/bin` included:
`open` propagates the caller's environment. The process is nonetheless a
genuine LaunchServices launch reparented to launchd —
`ps -o pid,ppid` gives ppid 1 (`/sbin/launchd`) — and it is not a stale
session variable either: `launchctl getenv PATH` prints nothing, rc=0.
So a measurement via `open` passes every "is this really a GUI launch?"
check anyone would think to run while carrying a contaminated PATH. Only
Finder, Dock or Spotlight gives the clean environment, and none of those
is reachable from a terminal.
REPRODUCIBLE SUBSTITUTE, used here: `env -i` with the minimal PATH,
verified on the live process rather than assumed.

**The run**:
```
$ rm -rf ~/Library/Application\ Support/tillandsias ~/Library/Caches/tillandsias   # skill's sanctioned macOS destroy step
$ test ! -e "$VM_DIR"   # verified gone

    "$HOME/Applications/Tillandsias.app/Contents/MacOS/tillandsias-tray"
```
